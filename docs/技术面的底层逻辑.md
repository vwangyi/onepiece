如何做性能优化。

我们就用刚才说的思路来答：先定位，再分层优化，最后建立防护，不堆清单。

第一步：先排查、量化，不要上来就改

不能凭感觉说页面卡。后台平台重点看这些指标：

• 加载阶段：LCP、资源瀑布、静态资源大小、接口串行请求

• 交互阶段：INP、长任务（long task），点按钮、切换菜单、表格排序会不会卡顿

• 运行时：频繁渲染、大量 DOM、内存泄漏（切页面后内存持续上涨）

手段：Chrome Performance、Network、Lighthouse、前端监控平台。
先分清瓶颈在哪：是网络？打包产物？渲染？JS 执行？后端接口慢？

后台平台有它独有的特点：页面多、表格多、弹窗多、权限逻辑重、经常 SPA 路由切换，C 端的图片优化反而不是重点。

第二层：构建与资源优化（加载阶段）

1. 分包策略
   路由懒加载，非首页业务页面按需引入；区分基础依赖、业务依赖。
   公共稳定依赖（Vue、React、组件库）单独拆包，走长效缓存。
   如果是微前端架构：基座公共依赖抽出来共享，避免多个子应用重复加载同一个框架。

2. 打包优化
   开启 Tree-Shaking，清理未使用代码；合理配置 externals 或者依赖外部 CDN（评估安全）；用 esbuild / SWC 提速构建，同时压缩产物。
   组件库按需引入，不要全量导入。

3. 缓存策略
   静态资源带 contenthash，强缓存；index.html 不长期缓存；接口做好合理缓存（SWR / 内存缓存，适合后台字典、权限这类不频繁变的数据）。

第三层：接口与数据层（后台最容易卡在这里）

后台很多慢，不是前端渲染，是接口。

• 避免串行请求：能并行就并行；权限、字典这类公共前置数据提前预加载。

• 大数据表格：禁止一次性返回全量数据，分页、滚动分页；后端配合字段裁剪，不要返回不需要的字段。

• 数据缓存：用户字典、枚举、菜单权限，短时间复用，减少重复请求；加加载状态、防抖，防止重复提交请求。

• 大体积返回：考虑接口分页、流式返回。

第四层：运行时渲染优化（切换页面、表格交互）

这一块是后台高频痛点。

• 列表表格：虚拟滚动，上万行数据不渲染全部 DOM；关闭不必要的响应式监听；避免在渲染模板里写复杂计算。

• 避免不必要重渲染：React 用好 memo、useMemo、useCallback；Vue 合理拆分组件，减少整块组件无意义更新。

• 长任务拆分：大量数据处理、导出、格式化，丢到 Web Worker，阻塞主线程会直接让交互变卡。

• 销毁清理：路由离开、子应用 unmount 的时候，清除定时器、事件监听、订阅，防止内存泄漏，越用越卡。

第五层：全局架构层面优化

• 权限逻辑不要在每个页面重复校验：基座统一处理，下发权限结果，页面只消费。

• 预加载：预判用户行为，比如进入菜单列表后，预加载大概率要打开的子页面 chunk，提升二次点击体验。

• 如果是微前端：做好子应用预加载、公共依赖共享，控制同时加载多个子应用带来的资源冲击。

• 渲染选型评估：部分页面如果首屏压力大，可以考虑 SSR；但后台内部系统很多时候 SPA 就足够，不要为了性能强行上 SSR 增加复杂度。

第六层：体验兜底优化（感知层面）

性能不只是指标数字，还有用户感受：

• 骨架屏、loading 占位，不要空白等待；

• 按钮、表格交互即时反馈，不要等接口返回才动；

• 大操作（导出、批量操作）提示后台异步处理，不要卡在页面。

第七层：保障机制，防止性能回退

优化做完不是结束：

• 接入监控：持续采集 LCP、INP、长任务、加载失败；

• 构建时增加产物体积告警，包变大了拦截提醒；

• 性能作为评审关注点，新增大组件、大量数据逻辑的时候提前评估；

• 定期复盘，版本上线后看线上指标变化。

补充取舍（面试加分项）

后台平台很多是内部系统，访问量不大，优先级要分清：

• 优先搞定：接口慢、大数据表格、内存泄漏、重复请求；

• 优先级低：图片压缩、极致的首屏体积压缩，收益有限；

• 警惕过度优化：为了一点点性能，写出难以维护的晦涩代码。

回答的收尾可以这样说：
后台平台性能优化，核心思路就是：先定位瓶颈，优先解决数据和长渲染，再优化加载，最后靠监控守住指标，持续演进，而不是一股脑堆优化手段。
