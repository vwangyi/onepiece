## 迪米特原则

面向对象设计 SOLID 五大原则之一
- 单一职责原则：一个函数只做一件事
- 开闭原则：封装模块应该 对扩展开放，对修改关闭。
- 里氏替换原则：子类可以扩展父类的功能，但不能改变父类原有的功能。
- 接口分离原则：不要一个接口实现所有增删改查
- 依赖倒置原则：原本两个模块直接依赖会导致耦合度增加。可以增加一层变为间接依赖从而降低耦合，比如vue的pinia，依赖数据状态而不是彼此依赖。 

- 迪米特原则：最小知道原则 封装模块传入参数越少越好，最好是不传参数。  

  


## 如何优化复杂度高的代码 
1. 用 单一职责原则 开闭原则 里氏替换原则 分成很多模块降低复杂度。 
2. 最后用依赖倒置原则 消除没必要的耦合
3. 虽然 业务压力 优先于 代码质量，但并不意味着屎山是理所当然，业务压力和代码质量应该权衡取舍，
4. 在大的架构模块上应该注重代码质量素质，在局部模块可临时放弃质量，局部模块虽然可能屎山 但这是可控的。
5. 作为管理着 应该负责大架构模块保证涉及全局的应该重视质量，而分出去的局部模块，则可以敏捷开发，不会涉及全局。

## 里氏替换原则 

里氏替换原则（Liskov Substitution Principle, LSP）是面向对象设计 SOLID 五大原则之一，由 Barbara Liskov 于 1987 年提出，核心定义：任何使用父类的地方，替换为其子类后，程序行为、语义和业务规则均保持正确 —— 重点是 “业务契约不变”，而非仅语法可编译。
一、核心本质：继承是 “契约承诺”
继承不仅复用代码，更承诺 “子类与父类是同一种东西”，需遵守父类所有公开契约（功能、前置 / 后置条件、异常约定等）。子类可扩展功能，但不能削弱或篡改父类已有行为，否则会破坏多态可信度。
二、经典反例（违反 LSP）

账户提现：父类Account有withdraw()（提现），子类FrozenAccount继承后重写该方法抛 “账户冻结” 异常。调用方用父类接收对象时，正常提现逻辑因子类异常崩溃，被迫加if-else判断类型，多态失效。
鸟类飞行：父类Bird定义fly()，子类Penguin（企鹅）重写fly()抛异常。调用方依赖Bird的 “会飞” 契约，替换后功能崩溃。

三、正确实现方式

拆分接口（推荐）：将 “能力” 与 “身份” 分离 —— 父类描述 “是什么”，接口描述 “能做什么”。
账户案例：父类Account（账户身份），接口Withdrawable（提现能力）；NormalAccount继承Account并实现Withdrawable，FrozenAccount仅继承Account。调用方通过接口判断能力，无需判断类型。
鸟类案例：父类Bird（鸟类身份），接口Flyable（飞行能力）；Sparrow实现Flyable，Penguin不实现。调用方依赖Flyable而非Bird调用fly()。


组合替代继承：子类无法遵守父类契约时，用 “包含父类实例” 替代继承，通过委托调用父类方法，避免篡改契约。
扩展而非修改：子类新增功能（如NormalAccount加 “快速提现”），不修改父类已有逻辑（如基础提现）。

四、违反后果与自查

后果：调用方堆砌if-else、接口语义混乱、修改子类引发全链路风险、继承体系崩塌。
自查三问：
子类是否削弱父类功能（如缩小范围、抛额外异常）？
调用方是否需判断子类类型才能安全调用？
子类是否改变父类业务含义（如正常行为变异常）？任一 “是” 即违反 LSP。



五、与开闭原则（OCP）关系
LSP 是 OCP 的基础：只有子类可安全替换父类，才能通过扩展（新增子类）而非修改父类扩展功能，二者共同支撑系统可扩展、低耦合。
总结
LSP 核心是 “契约一致性”：继承需保证 “父类能用的地方，子类必能用”。当子类无法遵守父类承诺时，优先用接口拆分 + 组合，而非继承，避免多态失效和系统僵化。

 

## 反模式
反模式就是不要过度使用设计模式，应该为了解决问题才用。
设计模式的最终目的是解决实际问题，应该为了解决问题才用，而不是为了用而用。

读框架源码：例如 Spring 中大量使用工厂模式（BeanFactory）、代理模式（AOP）、模板方法模式（JdbcTemplate）。
写业务重构：当你发现 if-else 过多时，尝试用策略模式+工厂模式改造；当对象构造参数过多时，用建造者模式。
反模式：知道什么时候不要用模式（过度设计是最大的敌人）。
