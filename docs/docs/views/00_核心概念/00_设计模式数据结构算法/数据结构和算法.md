## 线性数据结构之链表

一个存值 一个存下一个的指针引用 
```ts
const a = { value: 1, next: b };
const b = { value: 2, next: null }
```

链表是 存储空间上不连续。每存放一个值就多开销个引用空间。
好处就是 内存够一定存的下 没有空间碎片问题。
缺点：链表查询某个节点速度慢，每个节点都需要记录下一个节点的引用。



链表特性： 传递链表必须传递链表的根节点。每个节点都认为自己是根节点。

### ----------------------- 前端链表应用场景

前端日常开发中，**链表（LinkedList）**确实不像数组、对象那样天天写，但它在**底层框架、浏览器原理、高性能缓存**和**特殊交互场景**中扮演着极其关键的角色。

很多人觉得前端用不到链表，是因为被数组“可变长度+随机访问”的便利性宠坏了。但在以下 **7 大核心场景**中，链表凭借 **O(1) 时间复杂度的插入/删除**（无需移动元素）优势，是绝对的主角：

### 1. React 核心架构（Fiber 链表树）—— 最经典的工业级应用
这是前端领域链表最著名的应用。在 React 16+ 的 **Fiber 架构**中，每个虚拟 DOM 节点对应一个 Fiber Node，它们之间通过 **3 个链表指针**连接：

-   `child`：指向第一个子节点
-   `sibling`：指向下一个兄弟节点（**单向链表**）
-   `return`：指向父节点
React 利用这种**可中断的链表结构**，实现了“时间切片”（Concurrent Mode）。因为链表遍历是异步可中断的，遍历到一半可以暂停去处理高优先级任务，等会儿再接着来——这一点数组（需一次性遍历完）完全做不到。

### 2. 浏览器历史记录（History API）与 撤销/重做（Undo/Redo）
-   **路由历史**：浏览器维护的 `window.history` 底层本质上是一个**双向链表**（或栈+链表混合）。当你点击“后退/前进”时，本质上是沿着链表节点的 `prev`/`next` 指针移动。如果你在中途跳转并提交新页面，旧链表后续节点会被剪断（废弃），这就是标准的链表节点替换逻辑。
-   **在线文档（如富文本编辑器）**：要实现 `Ctrl+Z` 撤销，虽然常用“双栈”，但如果要实现**“跳转到任意历史节点”**（像 Git 回滚），链表结构比数组更省内存，因为只需保存变更指针，不需要深拷贝整个应用状态。

### 3. 前端缓存策略（LRU - 最近最少使用）
这是大厂面试高频题，也是实际业务（如浏览器缓存 Disk Cache、图片懒加载池）的核心。

-   **场景**：你封装一个本地数据缓存池，只存最近使用的 50 条数据。
-   **实现**：使用 **双向链表 + 哈希表（Map）**。当读取某个数据时，将该节点移动到链表头部；当缓存满了需要淘汰时，直接删除链表尾部的节点（最久未使用）。因为链表的删除和移动都是 `O(1)`，如果用数组（`unshift` + `pop`），每次移动都会导致数组所有元素下标重排，性能瞬间降为 `O(n)`。

### 4. 异步任务队列（宏任务/微任务调度）
虽然我们平时用 `setTimeout` 和 `Promise`，但浏览器事件循环（Event Loop）底层的任务队列（Task Queue）**并非简单的数组**。

-   为了维护不同优先级的任务（延时任务、交互任务、渲染任务），浏览器内核（如 Chromium）使用**优先级队列（通常基于链表或堆）**来管理。
-   当你大量使用 `requestAnimationFrame` 或消息通道（MessageChannel）时，链表用于高效地插入新任务和移除已执行任务，避免数组 `shift()` 操作带来的内存地址搬移开销。

### 5. 大文件分片上传 / 流式数据处理（Chunk）
当你处理超大文件（如几 GB 的视频上传）时，前端会使用 `Blob.slice()` 将文件切成若干 **Chunk（分片）**。

-   如果你需要实现**“断点续传”**和**“并发控制”**（比如最多同时传 3 片），未上传的分片列表、正在传输的分片、已完成的分片，用**单向链表**来管理极其方便。上传失败的分片只需挂在重试队列链表尾部，插入和剔除不影响已上传成功的分片索引（如果用数组，删除中间元素会导致索引错乱，需额外维护 `id`）。

### 6. 无限下拉列表 / 虚拟滚动（内存优化）
当列表有 10 万条数据时，虚拟滚动只渲染可视区域的 DOM。

-   虽然数据源往往是数组，但**渲染节点的缓存池（Recycle Pool）**通常使用链表。当节点滚出可视区，它会从 Dom 树移除并放入 **“空闲节点链表”**；当新节点滚入，从空闲链表中取出节点复用。这避免了频繁创建/销毁 DOM 带来的 GC（垃圾回收）卡顿。

### 7. 自定义中间件/插件链（AOP 切面编程）
类似于 Koa 或 Redux 的中间件（Middleware），虽然平时用数组存函数，但如果你要实现**“可动态插入/移除的流水线”**（如用户可在运行时动态禁用某个埋点中间件）：

-   链表比数组更适合。你可以给每个中间件节点挂载 `next` 指针，实现**洋葱模型**的动态变体。在运行时插入一个中间件，只需修改前后两个节点的指针，而不用像数组 `splice` 那样导致后续所有中间件下标重排。

### 💡 给你的实用建议（避坑）

-   **不要为了链表而链表**：如果你的数据量 **< 1000 条**，且不需要频繁在中间插入/删除，**请直接用数组**。因为数组是连续内存，CPU 缓存命中率高，`for` 循环遍历速度比链表快得多（链表 Node 对象分散在堆内存中，遍历存在大量指针跳跃，性能反而差）。
-   **如何判断用链表？** 问自己两个问题：① 是否频繁在**头部或中间**增删？② 是否几乎不需要按下标（`list[100]`）随机访问？两个答案都是“是”，链表才胜出。

如果你现在正遇到需要频繁 `splice` 大量数据导致页面卡顿的项目，可以考虑用 `Map` 维护 ID 映射 + 双向链表来重构。想知道具体怎么手写一个简洁的 LRU 缓存类供项目复用吗？我可以给你一段可直接运行的 TypeScript 模板。😊
