# 设计模式 
SOLID原则以及迪米特原则、组合聚合原则。
23种设计模式： 
创建型（5种）：关注“对象如何产生”。重点学 工厂模式、建造者模式、单例模式。
结构型（7种）：关注“类与类如何组合”。重点学 适配器模式、装饰器模式、代理模式。
行为型（11种）：关注“对象间如何交互”。重点学 策略模式、观察者模式、责任链模式、模板方法模式。


这是区分初级和中级程序员的分水岭。你需要能回答出：
策略模式 vs 状态模式（前者封装算法，后者封装状态机）。
代理模式 vs 装饰器模式（前者控制访问，后者增强功能）。
工厂模式 vs 抽象工厂模式（前者生产单一种类，后者生产产品族）。
组合 vs 继承：什么时候用组合？答案是“当继承会造成类爆炸时”。


设计模式的最终目的是解决实际问题，而不是为了用而用。
读框架源码：例如 Spring 中大量使用工厂模式（BeanFactory）、代理模式（AOP）、模板方法模式（JdbcTemplate）。
写业务重构：当你发现 if-else 过多时，尝试用策略模式+工厂模式改造；当对象构造参数过多时，用建造者模式。
反模式：知道什么时候不要用模式（过度设计是最大的敌人）。

手打一遍单例、工厂、策略、观察者这 4 个模式。
把你过去项目里一个 100 行的 if-else 方法，用策略模式重构。

复杂度是什么：复杂度高。 代码质量不高 可维护性差 复用性差 扩展性差 （所有功能都写道一个函数里面 复杂度就高）




开发流程：
1. 优先降低复杂度，尽量降低耦合度
2. 利用单一职责原则，开闭原则，里氏替换原则。 增加耦合度 降低复杂度。
3. 迪米特法则 减少耦合度
3. 依赖倒置原则 消除可以没有的耦合



面向对象设计 SOLID 五大原则之一
- 单一职责原则：一个函数只做一件事
- 开闭原则：封装模块应该 对扩展开放，对修改关闭。
- 里氏替换原则：子类可以扩展父类的功能，但不能改变父类原有的功能。
- 接口分离原则：不要一个接口实现所有增删改查
- 依赖倒置原则：原本两个模块直接依赖会导致耦合度增加。可以增加一层变为间接依赖从而降低耦合，比如vue的pinia，依赖数据状态而不是彼此依赖。 



- 迪米特法则：最小知道原则 封装模块传入参数越少越好，最好是不传参数。
  
代码质量是高度是素质高低。学会权衡才是高价值的开发经验。


优化复杂度高的代码 
1. 用 单一职责原则 开闭原则 里氏替换原则 分成很多模块降低复杂度。

3. 虽然 业务压力 优先于 代码质量，但并不意味着屎山是理所当然，业务压力和代码质量应该权衡取舍，

5. 作为管理着 应该负责大架构模块保证涉及全局的应该重视质量，而分出去的局部模块，则可以敏捷开发，不会涉及全局。

## 单例模式

- 定义：整个应用只有一个实例。比如 vuex/pinia。 应用场景是创建对象时。不管创建多少次都是同一个对象。

比如 一个登录弹窗对象，没有必要每次点开弹窗都创建一个新的。


## 代理模式
- 代理模式：给一个对象 提供的 代理对象，通过这个代理对象 来访问原对象。 类似中介，代理对象可能删除或增加一些功能。
- 虚拟代理：虚拟代理

虚拟代理：虚拟代理是把一些开销很大的对象，延迟到真正需要它的时候才去创建执行， 图片懒加载 图片预加载 文件上传
安全代理（保护代理）：控制真实对象的访问权限 （登录后才可以看全功能 前端校验）
远程代理：（一个对象将不同空间的对象进行局部代理）监控多个对象的状态 总店监控分店
智能代理：（调用对象代理处理另外一些事情如垃圾回收机制增加额外的服务） 提供额外的其他服务 比如 火车站代售点

## 策略模式

策略模式是指对一系列的算法定义，并将每一个算法封装起来，而且使它们还可以相互替换。策略模式让算法独立于使用它的客户而独立变化。

策略模式的优点有：策略模式提供了管理相关的算法族
的办法、策略模式提供了可以替换继承关系的办法、使
用策略模式可以避免使用多重条件转移语句。


策略模式支持您在运行时选择算法,把他们一个个封装
起来，并且使他们可以相互替换。
决定用一个类对象实例来管理规则的校验
该对象要能，相应的主动添加对规则的相应处理办法
校验数据的时候可以相应的返回相关信息

## 工厂模式
定义:工厂模式定义创建对象的接口，但是让子类去真正的实例化。也就是工厂方法将类的实例化延迟到子类

比如 createApp

设计模式-工厂模式-对比其他方式
1.工厂类集中了所有对象的创建，便于对象创建的统一管理
2.对象的使用者仅仅是使用产品，实现了单一职责
3.便于扩展，如果新增了一种业务，只需要增加相关的业务 对象类和工厂类中的生产业务对象的方法，不需要修改其他的地方。
4.确实违反了开闭原则


## 工厂方法模式
设计模式-工厂方法模式
工厂方法模式：
不再有一个唯一的工厂类就创建产品，而是将不同的产品交给对应的工厂子类去实现。每个产品由负责生产的子工厂来创造。
如果添加新的产品，需要做的是添加新的子工厂和产品，而不需要修改其他的工厂代码。


设计模式-工厂方法模式组成
1. 抽象工厂类：负责定义创建产品的公共接口。
2. 产品子工厂：继承抽象工厂类，实现抽象工厂类提供的接口
3. 每一种产品有各自的产品类

设计模式-工厂方法模式
代码比简单工厂模式复杂了，引入了抽象层，还有子工
厂，这会增加代码的复杂度和理解难度。但是相比于简
单工厂模式，代码的维护性和扩展性提高了，新增产品
时，只需要增加对应的产品类和产品工厂类，不需要修
改到抽象工厂类和其他子工厂。更加符合面向对象的开
放封闭原则。
当然具体场景具体分析 复杂性和扩展课相如何舍去
在使用的时候要结合实际场景去分析。



## 装饰者模式
设计模式-装饰者模式

装饰者(decorator)模式能够在不改变对象自身的基础上，
在程序运行期间给对像动态的添加职责。与继承相比，装
饰者是一种更轻便灵活的做法。可以当脚本运行时，在子
类中增加行为会影响原有类所有的实例，而装饰者却不然。
取而代之的是它能给不同对象各自添加新行为

实现:构造函数需要一个装饰资源池，提供相应的装饰方
法，提供添加装饰方法的方法。


## 观察者模式
设计模式-观察者模式

当一个对象的状态发生改变时，所有依赖于它的对象都将

## 里氏替换原则

里氏替换原则（Liskov Substitution Principle, LSP）是面向对象设计 SOLID 五大原则之一，由 Barbara Liskov 于 1987 年提出，核心定义：任何使用父类的地方，替换为其子类后，程序行为、语义和业务规则均保持正确 —— 重点是 “业务契约不变”，而非仅语法可编译。
一、核心本质：继承是 “契约承诺”
继承不仅复用代码，更承诺 “子类与父类是同一种东西”，需遵守父类所有公开契约（功能、前置 / 后置条件、异常约定等）。子类可扩展功能，但不能削弱或篡改父类已有行为，否则会破坏多态可信度。
二、经典反例（违反 LSP）

账户提现：父类Account有withdraw()（提现），子类FrozenAccount继承后重写该方法抛 “账户冻结” 异常。调用方用父类接收对象时，正常提现逻辑因子类异常崩溃，被迫加if-else判断类型，多态失效。
鸟类飞行：父类Bird定义fly()，子类Penguin（企鹅）重写fly()抛异常。调用方依赖Bird的 “会飞” 契约，替换后功能崩溃。

三、正确实现方式

拆分接口（推荐）：将 “能力” 与 “身份” 分离 —— 父类描述 “是什么”，接口描述 “能做什么”。
账户案例：父类Account（账户身份），接口Withdrawable（提现能力）；NormalAccount继承Account并实现Withdrawable，FrozenAccount仅继承Account。调用方通过接口判断能力，无需判断类型。
鸟类案例：父类Bird（鸟类身份），接口Flyable（飞行能力）；Sparrow实现Flyable，Penguin不实现。调用方依赖Flyable而非Bird调用fly()。


组合替代继承：子类无法遵守父类契约时，用 “包含父类实例” 替代继承，通过委托调用父类方法，避免篡改契约。
扩展而非修改：子类新增功能（如NormalAccount加 “快速提现”），不修改父类已有逻辑（如基础提现）。

四、违反后果与自查

后果：调用方堆砌if-else、接口语义混乱、修改子类引发全链路风险、继承体系崩塌。
自查三问：
子类是否削弱父类功能（如缩小范围、抛额外异常）？
调用方是否需判断子类类型才能安全调用？
子类是否改变父类业务含义（如正常行为变异常）？任一 “是” 即违反 LSP。



五、与开闭原则（OCP）关系
LSP 是 OCP 的基础：只有子类可安全替换父类，才能通过扩展（新增子类）而非修改父类扩展功能，二者共同支撑系统可扩展、低耦合。
总结
LSP 核心是 “契约一致性”：继承需保证 “父类能用的地方，子类必能用”。当子类无法遵守父类承诺时，优先用接口拆分 + 组合，而非继承，避免多态失效和系统僵化。
